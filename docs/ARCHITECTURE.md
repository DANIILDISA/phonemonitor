# PhoneMonitor — архитектура системы

Документ описывает устройство системы, обоснование ключевых решений и бюджет
задержки. Читать вместе с `README.md` (обзор) и `docs/BUILD.md` (сборка).

---

## 1. Задача и ограничения

Превратить Android-устройство во вторичный монитор Windows 10/11 через USB
с целевой сквозной задержкой **менее 30 мс**.

Ограничения, определившие архитектуру:

| Ограничение | Следствие |
|---|---|
| `WUDFHost.exe` под надзором PnP-менеджера | В драйвере нельзя кодировать видео и работать с сетью — только отдать монитор и скопировать кадр |
| Драйвер в сессии 0, стример в сессии пользователя | Все объекты IPC в пространстве имён `Global\` с явной DACL |
| Кадр живёт в видеопамяти | Ни одного прохода через системную память на всём пути Windows |
| USB через adb — надёжный, но не бесконечный канал | CBR 15 Мбит/с, VBV в один кадр, отказ от накопления буферов |
| Аппаратный декодер телефона имеет предел разрешения | Согласование геометрии до начала кодирования |
| Декодер греет телефон | Реакция на первый же сигнал `THERMAL_STATUS_LIGHT` |

## 3. Компонент 1 — драйвер косвенного дисплея

**Расположение:** `driver/`
**Технологии:** UMDF 2.0, IddCx, D3D11.4, WDK 10+

### 3.1 Жизненный цикл

```
DriverEntry
  └─ WdfDriverCreate
EvtDriverDeviceAdd
  ├─ IddCxDeviceInitConfig     ← обязательно ДО WdfDeviceCreate
  ├─ WdfDeviceCreate
  └─ IddCxDeviceInitialize
EvtDeviceD0Entry
  ├─ IpcServer::Start          ← секция создаётся ДО объявления монитора
  └─ IddCxAdapterInitAsync
EvtIddCxAdapterInitFinished
  ├─ IddCxMonitorCreate
  └─ IddCxMonitorArrival       ← монитор появляется в «Параметрах экрана»
EvtIddCxMonitorAssignSwapChain
  ├─ Direct3DDevice::Init      ← на LUID адаптера отрисовки
  ├─ IpcServer::AttachDevice   ← создание общего фенса
  └─ SwapChainProcessor::Start
```

Инициализация адаптера вынесена в `EvtDeviceD0Entry`, а не в `EvtDriverDeviceAdd`:
на момент `DeviceAdd` стек устройства ещё не поднят и `IddCxAdapterInitAsync`
возвращает ошибку.

### 3.2 Горячий путь кадра

`SwapChainProcessor::ProcessFrames` → `IndirectDeviceContext::DeviceTransmit`
→ `IpcServer::PublishFrame`:

1. `IddCxSwapChainReleaseAndAcquireBuffer` — **без предварительного ожидания**.
   Сначала пробуем забрать кадр; уход в `WaitForMultipleObjects` до попытки
   чтения стоил бы лишнего переключения контекста (50–200 мкс) на каждом кадре.
2. `QueryInterface` → `ID3D11Texture2D`.
3. `CopyResource` в текущий слот кольца.
4. `ID3D11DeviceContext4::Signal(fence, ++counter)`.
5. `Flush()` — без него копия может пролежать в очереди драйвера десятки мс.
6. Публикация метаданных **в строгом порядке**: слот, значение фенса, QPC,
   барьер, и только затем `frameIndex`.
7. `SetEvent(FrameReady)`.
8. `IddCxSwapChainFinishedProcessingFrame` — обязательный парный вызов.

Поток захвата работает в классе MMCSS `Distribution` с приоритетом
`AVRT_PRIORITY_CRITICAL`.

### 3.3 Динамическая смена разрешения

Запрос приходит от стримера через разделяемую память
(`modeRequestSerial` + событие `ModeRequest`). Служебный поток `IpcServer`
вызывает `IndirectDeviceContext::ApplyDisplayMode`, который:

1. выравнивает размеры вниз до кратного 16 (макроблок H.264);
2. пересобирает таблицу режимов и EDID под новое разрешение;
3. вызывает `DisplayModesSet`.

`DisplayModesSet` имеет два пути:

* **Быстрый** (`PM_HAVE_IDDCX_UPDATEMODES`, IddCx 1.9+): `IddCxMonitorUpdateModes`
  меняет список режимов без отключения монитора. Рабочий стол не мигает.
  Макрос выставляется CMake автоматически, если функция найдена в заголовках WDK.
* **Универсальный**: `UnassignSwapChain` → `IddCxMonitorDeparture` → пауза 120 мс
  → `IddCxMonitorCreate` + `IddCxMonitorArrival` с новым EDID. Для системы это
  выглядит как переподключение кабеля; занимает 300–700 мс.

EDID генерируется на лету (`MonitorModes.cpp`): подробный дескриптор
синхронизации описывает ровно запрошенный режим и помечается предпочтительным,
физический размер вычисляется исходя из диагонали 6.5″ с сохранением пропорций —
это напрямую определяет DPI, который Windows предложит пользователю.

## 4. Механизм IPC

**Контракт:** `common/pm_ipc.h` (версия 3).

### 4.1 Объекты

| Объект | Имя | Создаёт |
|---|---|---|
| Секция 64 КиБ | `Global\PhoneMonitor.SharedState.v3` | драйвер |
| Мьютекс | `Global\PhoneMonitor.Mutex.v3` | драйвер |
| События | `...FrameReady` / `ModeRequest` / `HandleRequest` / `HandleReady` | драйвер |
| Текстуры (3 шт.) | `Global\PhoneMonitor.Tex.<серия>.<слот>` | драйвер |
| Фенс | безымянный, передаётся дублированием | драйвер |

Ко всем объектам применяется DACL
`D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGWGX;;;AU)` — иначе объекты, созданные в
сессии 0 из-под SYSTEM, недоступны пользовательскому процессу.

### 4.2 Передача текстур

`IDXGIResource1::CreateSharedHandle` с **именем** → стример открывает через
`ID3D11Device1::OpenSharedResourceByName`. Именованное разделение избавляет от
дублирования хендлов для текстур.

Требуемая комбинация флагов ресурса: `D3D11_RESOURCE_MISC_SHARED |
D3D11_RESOURCE_MISC_SHARED_NTHANDLE`. Имя живёт, пока драйвер держит хендл
открытым.

### 4.3 Передача фенса

Фенс **нельзя** открыть по имени: в D3D11 нет `OpenSharedFenceByName`.
Поэтому реализована схема «запрос-ответ»:

```
стример:  streamerPid = GetCurrentProcessId()
          SetEvent(HandleRequest)
драйвер:  OpenProcess(PROCESS_DUP_HANDLE, streamerPid)
          DuplicateHandle(наш фенс → процесс стримера)
          fenceHandleValue = дубликат; ++fenceHandleSerial
          SetEvent(HandleReady)
стример:  m_device5->OpenSharedFence(значение)
```

Дублирование делает **драйвер**, а не стример: драйвер работает с более
высокими привилегиями, а обратное направление потребовало бы от стримера права
на открытие `WUDFHost.exe`.

### 4.4 Поиск адаптера

LUID адаптера драйвера не передаётся явно. Стример определяет его эмпирически:
перебирает адаптеры DXGI, создаёт на каждом устройство и пробует открыть
текстуру нулевого слота. Первый успех и есть нужный адаптер. На типовой машине
это 1–2 итерации, и такой подход автоматически корректен при гибридной графике.

### 4.5 Согласованное чтение кадра

Драйвер пишет `frameIndex` **последним**, стример читает его **первым**:

```cpp
for (attempt = 0; attempt < 4; ++attempt) {
    frameIndex = header->frameIndex;   MemoryBarrier();
    slot = header->slot;  fenceValue = header->fenceValue;  presentQpc = ...;
    MemoryBarrier();
    if (frameIndex == header->frameIndex) { consistent = true; break; }
}
```

Если `frameIndex` изменился за время чтения — драйвер опубликовал новый кадр,
и прочитанное описание может относиться уже к нему. Повторяем.

## 5. Компонент 2 — стример

**Расположение:** `streamer/`

### 5.1 Путь кадра

```
IpcClient::AcquireFrame
  ├─ WaitForSingleObject(FrameReady, 250 мс)
  ├─ согласованное чтение метаданных
  ├─ ctx4->Wait(fence, fenceValue)       ← синхронизация НА GPU, CPU не блокируется
  └─ CopyResource(приватная текстура ← слот)
        │
        ▼
IVideoEncoder::EncodeFrame               ← NVENC или MFT
        │
        ▼
TcpTransport::SendAll                    ← сырой Annex B
```

Кадр копируется в приватную текстуру стримера, а не кодируется прямо из слота:
драйвер циклически переиспользует слоты, и через `PM_RING_SLOTS` кадров начнёт
писать в тот же слот. Один блит (доли миллисекунды) снимает вопрос разрывов
картинки и делает время жизни кадра в кодировщике неограниченным.

### 5.2 Бэкенды кодирования

| Бэкенд | Вход | Intra-Refresh | Когда используется |
|---|---|---|---|
| **NVENC** (`nvEncodeAPI64.dll`) | BGRA напрямую | ✅ полноценный | NVIDIA, основной путь |
| **Media Foundation MFT** | NV12 (конверсия видеопроцессором) | ❌ — IDR по запросу | AMD (AMF), Intel (QuickSync) |

**Почему AMD и Intel через MFT, а не через AMF SDK и oneVPL напрямую.**
MFT для AMD является официальной обёрткой над AMF и поставляется с драйвером
Adrenalin; MFT Intel — рекомендованный Intel способ доступа к QuickSync из
приложений Windows. Оба дают доступ к тем же аппаратным блокам, сохраняют
конвейер без копий в системную память (через `IMFDXGIDeviceManager`) и не
требуют ничего, кроме Windows SDK. Линковка с двумя дополнительными SDK
добавила бы два рантайма и два жизненных цикла устройства ради того же
кремния.

**Ограничение, о котором нужно знать явно:** `ICodecAPI` не содержит
переносимого свойства для управления волной внутрикадрового обновления — у AMD
и Intel это приватные расширения их SDK. Поэтому Intra-Refresh с полосой 5 %
реализован **только на пути NVENC**. На пути MFT устойчивость обеспечивается
иначе: TCP гарантирует доставку (потери пакетов как таковой нет), клиент может
запросить IDR сообщением `PM_MSG_KEYFRAME_REQ`, и IDR выдаётся при любом
пересоздании или переконфигурации кодировщика.

### 5.3 Настройки NVENC под низкую задержку

```cpp
presetGUID              = NV_ENC_PRESET_LOW_LATENCY_HP_GUID
tuningInfo              = NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY
gopLength               = NVENC_INFINITE_GOPLENGTH
frameIntervalP          = 1                     // только P-кадры, без B
h264.idrPeriod          = NVENC_INFINITE_GOPLENGTH
rcParams.rateControlMode= NV_ENC_PARAMS_RC_CBR
rcParams.vbvBufferSize  = битрейт / fps         // буфер ровно в один кадр
rcParams.vbvInitialDelay= то же
enableEncodeAsync       = 0                     // синхронный режим
h264.enableIntraRefresh = 1
h264.intraRefreshCnt    = 100 / 5 = 20          // полоса 5 % ширины
h264.intraRefreshPeriod = max(fps, 20)
h264.repeatSPSPPS       = 1
```

Базовая конфигурация берётся **из пресета** и точечно переопределяется:
NVENC хранит в пресете десятки полей, часть которых не документирована, и
заполнение их вручную регулярно приводит к `NV_ENC_ERR_INVALID_PARAM`.

VBV размером в один кадр — краеугольный камень: кодировщик не может «занимать»
биты у будущих кадров, а значит и накапливать задержку на стороне декодера.

### 5.4 Сеть

Стример — **клиент**, телефон — **сервер**. `adb forward tcp:6100 tcp:6100`
пробрасывает локальный порт ПК в порт внутри устройства.

Настройки сокета:

* `TCP_NODELAY` — без него мелкие NAL (SPS, PPS, SEI) копятся до 200 мс;
* `SO_SNDBUF = 64 КиБ` (≈2 кадра) — намеренно небольшой: большой буфер прячет
  затор и превращает его в скрытую задержку вместо честной блокировки;
* `SO_SNDTIMEO = 2000 мс` — зависший телефон не должен блокировать конвейер;
* `SO_KEEPALIVE` — обрыв кабеля не всегда закрывает сокет немедленно.

### 5.5 Управление ADB

`AdbBridge` ищет `adb.exe` в порядке: явный путь → `PATH` → каталог рядом с
исполняемым файлом → `ANDROID_HOME`/`ANDROID_SDK_ROOT` →
`%LOCALAPPDATA%\Android\Sdk\platform-tools` → `%ProgramFiles%\Android\...` →
Scoop/Chocolatey.

Запуск через анонимный канал с `CREATE_NO_WINDOW` (не `system()`): нужен вывод
и недопустимо мигающее окно консоли. Наследуется **только** пишущий конец
канала — иначе `ReadFile` никогда не вернёт EOF.

Снятие форварда гарантируется тремя путями: деструктор `AdbBridge`,
`StreamSession::EmergencyCleanup` и обработчик консольных сигналов
(`CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT`, `CTRL_SHUTDOWN_EVENT`). Перед
созданием форварда снимается возможный «висячий» с прошлого запуска.

## 6. Компонент 3 — Android-клиент

**Расположение:** `android-client/`
**minSdk 26, targetSdk 34, Kotlin, без сторонних зависимостей**

### 6.1 Потоки

| Поток | Приоритет | Роль |
|---|---|---|
| Главный (UI) | обычный | SurfaceView, `FLAG_KEEP_SCREEN_ON`, накладка состояния |
| `PhoneMonitor-Network` | `THREAD_PRIORITY_URGENT_AUDIO` | `ServerSocket`, чтение, разбор NAL |
| `PhoneMonitor-Decoder` | `THREAD_PRIORITY_URGENT_AUDIO` | MediaCodec, вывод на Surface |
| `PhoneMonitor-Thermal` | `MIN_PRIORITY` | опрос нагрева раз в 10 с |

Ни один байт видеопотока не проходит через главный поток.

### 6.2 Разбор NAL — скользящее окно

```
[ ...обработано... | НАЧАЛО текущего NAL ... хвост... ]
                    ^nalStart          ^dataEnd
                              ^searchPosition
```

`searchPosition` гарантирует, что каждый байт просматривается ровно один раз —
сложность O(n) от объёма потока. После разбора позиция откатывается на 3 байта:
там может начинаться стартовый код, чей хвост придёт со следующим `read`.

Обрабатываются оба варианта стартового кода (`00 00 01` и `00 00 00 01`) — они
встречаются в одном потоке: кодировщики ставят четырёхбайтовый перед
SPS/PPS/IDR и трёхбайтовый перед остальными.

**Восстановление после повреждения.** NAL отбрасывается, если он пустой,
превышает лимит размера, имеет установленный `forbidden_zero_bit` или тип 0 /
24–31. Никакого сложного восстановления не требуется: стартовые коды и есть
точки ресинхронизации, заложенные в формат. Разборщик просто продолжает искать
следующий стартовый код.

Управление буфером: сначала уплотнение (сдвиг полезного хвоста влево), и только
если места всё равно не хватает — удвоение ёмкости. При росте свыше
`maxNalSize * 2` без единого стартового кода поток считается сбитым и
разборщик сбрасывается.

### 6.3 MediaCodec

```kotlin
format.setInteger(MediaFormat.KEY_LATENCY, 0)           // не копить кадры
format.setInteger(MediaFormat.KEY_PRIORITY, 0)          // реальное время
format.setInteger(MediaFormat.KEY_LOW_LATENCY, 1)       // API 30+: без переупорядочивания
format.setInteger(MediaFormat.KEY_OPERATING_RATE, Short.MAX_VALUE.toInt())
decoder.configure(format, surface, null, 0)
```

Цикл:

```kotlin
inputIndex = decoder.dequeueInputBuffer(10_000)        // ≤ 10 мс по спецификации
decoder.queueInputBuffer(inputIndex, 0, len, ptsUs, flags)

outputIndex = decoder.dequeueOutputBuffer(info, 0)     // неблокирующе
while (outputIndex >= 0) {
    decoder.releaseOutputBuffer(outputIndex, true)     // render = true
    outputIndex = decoder.dequeueOutputBuffer(info, 0)
}
```

Выдача — **в цикле**: декодер мог накопить несколько кадров, и забрать нужно
все, иначе они добавятся к задержке. Вариант
`releaseOutputBuffer(index, timestamp)` не используется намеренно — он
задерживает вывод до указанного момента.

`SurfaceView`, а не `TextureView`: SurfaceView отдаёт декодеру отдельный слой
аппаратного композитора, минуя конвейер отрисовки приложения. TextureView
потребовал бы прохода через GPU приложения и добавил бы кадр задержки.

### 6.4 Очередь и политика вытеснения

Глубина очереди — 8 NAL (≈2–3 кадра). Глубина очереди это **прямое слагаемое
сквозной задержки**, поэтому она намеренно мала.

При переполнении вытесняется **самый старый** пакет, а не новый: показать
свежий кадр с артефактами лучше, чем корректный, но устаревший — пользователь
двигает мышью здесь и сейчас. Исключение — SPS/PPS и IDR: без них декодер не
восстановится, поэтому они не вытесняются, и вместо них отбрасывается новый
пакет. После вытеснения отправляется `PM_MSG_KEYFRAME_REQ`.

Буферы пакетов берутся из предзаполненного пула: при 60 кадрах в секунду
выделение массива на каждый NAL заставило бы сборщик мусора работать
непрерывно, а каждая его пауза — это пропущенный кадр.

## 7. Согласование геометрии

```
Android                          Стример                        Драйвер
───────                          ───────                        ───────
WindowManager.maximumWindowMetrics
MediaCodecList → предел декодера
       │
       ├─ PM_MSG_HELLO ─────────▶ проверка предела декодера
                                  масштабирование с сохранением пропорций
                                  выравнивание вниз до кратного 16
                                         │
                                         ├─ requestedW/H + ++serial ──▶ ApplyDisplayMode
                                         │   SetEvent(ModeRequest)      DisplayModesSet
                                         │                              (UpdateModes либо
                                         │                               departure/arrival)
                                         ◀── modeAppliedSerial ─────────┘
                                  сверка с activeWidth/Height
                                  создание кодировщика
```

Ключевой момент: **физическое разрешение экрана и предел декодера — разные
вещи**. Устройства с экраном 2400×1080 нередко имеют декодер, ограниченный
1920×1080. Превышение даёт либо отказ `MediaCodec`, либо молчаливый переход на
программный декодер с задержкой в сотни миллисекунд.

Пределы декодера нормализуются по ориентации: декодеры объявляют их в
альбомной системе координат (4096×2304), а экран телефона портретный —
прямое сравнение дало бы ложное превышение по высоте.

## 8. Тепловой режим

```
PowerManager.OnThermalStatusChangedListener (API 29+)
  либо оценка по BatteryManager.EXTRA_TEMPERATURE (API 26–28)
        │
        ├─ дедупликация (одно и то же значение не отправляется повторно)
        │
        └─ PM_MSG_THERMAL ──▶ StreamSession::ApplyThermalState
                                   │
                                   ├─ IpcClient::SetQualityFlags(PM_QF_THERMAL_SAVE)
                                   ├─ IpcClient::RequestMode(720p с пропорциями)
                                   └─ битрейт → 6 Мбит/с
```

Порог срабатывания — `THERMAL_STATUS_LIGHT`, самый ранний сигнал. Реагировать
рано выгодно: снижение нагрузки на этом этапе предотвращает жёсткий троттлинг,
при котором декодер начинает пропускать кадры и задержка растёт лавинообразно,
а восстановиться сама система уже не может, пока не остынет.

Возврат к полному разрешению происходит при нормализации состояния.
Отключается ключом `--no-thermal`.

На API 26–28 `getCurrentThermalStatus` отсутствует, используется грубая оценка
по температуре батареи (пороги 39 / 42 / 45 °C). Батарея греется медленнее
кристалла, поэтому пороги подобраны с запасом.

## 9. Бюджет задержки

Оценка для 1920×1080 @ 60 Гц, NVENC, USB 3.0:

| Этап | Типично | Комментарий |
|---|---|---|
| Композиция DWM → swapchain | 1–2 мс | вне нашего контроля |
| `ReleaseAndAcquireBuffer` + `CopyResource` + `Flush` | 0.3–0.8 мс | блит в видеопамяти |
| IPC: событие + согласованное чтение | 0.05–0.2 мс | lock-free, без мьютекса в горячем пути |
| Ожидание фенса + копия в приватную текстуру | 0.2–0.5 мс | синхронизация на GPU, CPU свободен |
| Кодирование NVENC (LOW_LATENCY_HP) | 2–5 мс | синхронный режим, VBV в один кадр |
| Передача по USB (adb, 15 Мбит/с) | 2–6 мс | зависит от версии USB и кабеля |
| Разбор NAL | < 0.1 мс | O(n), без выделений памяти |
| Декодирование MediaCodec | 4–10 мс | `KEY_LOW_LATENCY`, без B-кадров |
| Композиция Android → панель | 8–16 мс | один кадр панели |
| **Итого** | **17–41 мс** | цель < 30 мс достижима при 60 Гц панели |

Наибольший неустранимый вклад — композиция на стороне Android (один период
панели). На устройствах с панелью 120 Гц этот вклад падает вдвое, и общая
задержка укладывается в 20–25 мс.

Измерение: стример считает `presentQpc` (момент публикации драйвером) до
момента успешной отправки в сокет и выводит среднюю и пиковую задержку каждые
`--stats-interval` кадров. Клиент отдельно присылает задержку декодирования в
`PM_MSG_STATS`.

## 10. Обработка ошибок и восстановление

| Ситуация | Реакция |
|---|---|
| Драйвер не установлен | Стример ждёт секцию `--driver-wait` мс, затем внятная диагностика |
| Несовпадение версии IPC | Жёсткий отказ: работа с чужой раскладкой портит память |
| Телефон не подключён / не авторизован | `AdbBridge` различает `device` / `unauthorized` / `offline` и подсказывает действие |
| Клиент не запущен | `connect` повторяется каждые 400 мс до `--connect-timeout` |
| Разрыв соединения | `TeardownSession` + переподключение через 2 с (отключается `--no-reconnect`) |
| Смена режима в Windows | Размер кадра — источник истины; кодировщик переконфигурируется или пересоздаётся |
| Потеря устройства GPU | Выход из цикла захвата; IddCx пересоздаёт swapchain и вызывает `AssignSwapChain` |
| `MediaCodec.CodecException` | `isTransient` → продолжаем; `isRecoverable` → `reset` + `configure` + запрос IDR; иначе — фатально |
| Рассинхронизация управляющего канала | Разрыв соединения: в отличие от видеопотока, точек ресинхронизации здесь нет |
| Повреждённый NAL | Отбрасывается, разбор продолжается со следующего стартового кода |
