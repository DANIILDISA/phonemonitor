# PhoneMonitor

Вторичный монитор Windows 10/11 на экране Android-устройства через USB.
Целевая сквозная задержка — **менее 30 мс**.

Система написана с нуля: драйвер косвенного дисплея, приложение-стример и
нативный Android-клиент. Сторонних зависимостей нет — только Windows SDK/WDK
и платформенные API Android.

```
Рабочий стол Windows → виртуальный монитор (IddCx) → разделяемая видеопамять
    → аппаратный H.264 → TCP через adb (USB) → MediaCodec → SurfaceView
```

## Ключевые решения

**Драйвер не кодирует и не работает с сетью.** `WUDFHost.exe` находится под
надзором PnP-менеджера: длительная операция в нём приводит к таймауту старта
устройства и принудительной перезагрузке драйвера. Драйвер делает ровно две
вещи — отдаёт системе виртуальный монитор и копирует кадры в разделяемую
видеопамять.

**Кадр не покидает видеопамять на всём пути Windows.** Драйвер копирует
поверхность swapchain в общую текстуру, стример открывает её на том же
адаптере, синхронизируется через `ID3D11Fence` (синхронизация на стороне GPU —
процессор не блокируется) и отдаёт прямо в кодировщик.

**Три слота, один фенс, lock-free публикация.** Драйвер пишет `frameIndex`
последним, стример читает его первым и перепроверяет после чтения описания.
Мьютекса в горячем пути нет.

**Разрешение диктует телефон.** Клиент первым пакетом сообщает физическую
геометрию экрана **и предел аппаратного декодера** — это разные вещи, и
устройства с экраном 2400×1080 нередко имеют декодер до 1920×1080. Стример
согласует размер, выравнивает под макроблоки H.264 и просит драйвер
динамически сменить режим.

**Задержка не прячется в буферах.** VBV кодировщика — ровно один кадр,
`SO_SNDBUF` — два кадра, очередь декодера — восемь NAL. Большой буфер не
устраняет затор, а превращает его в скрытую задержку.

**Реакция на нагрев — на первом же сигнале.** `THERMAL_STATUS_LIGHT` включает
режим 720p. Ждать жёсткого троттлинга нельзя: из него система не выходит, пока
не остынет.

## Быстрый старт

```powershell
# 1. Собрать драйвер (нужен WDK)
cmake -S driver -B build/driver -A x64 -DWDK_ROOT="C:/Program Files (x86)/Windows Kits/10"
cmake --build build/driver --config Release

# 2. Установить (тестовый режим подписи, от администратора)
bcdedit /set testsigning on      # и перезагрузка
pnputil /add-driver build\driver\Release\PhoneMonitor.inf /install
devgen /add /hardwareid "Root\PhoneMonitorIdd"

# 3. Собрать стример
cmake -S streamer -B build/streamer -A x64
cmake --build build/streamer --config Release

# 4. Собрать и поставить клиент
cd android-client && .\gradlew.bat installRelease

# 5. Запустить приложение на телефоне, затем:
.\build\streamer\Release\phonemonitor-streamer.exe
```

Подробности, подпись драйвера и диагностика — в [`docs/BUILD.md`](docs/BUILD.md).
Устройство системы и бюджет задержки — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Поддержка кодировщиков

| GPU | Путь | Intra-Refresh |
|---|---|---|
| NVIDIA | NVENC напрямую (`nvEncodeAPI64.dll`, динамическая загрузка) | ✅ полоса 5 % ширины кадра |
| AMD | Media Foundation MFT (официальная обёртка над AMF) | ❌ IDR по запросу клиента |
| Intel | Media Foundation MFT (QuickSync) | ❌ IDR по запросу клиента |

`ICodecAPI` не содержит переносимого свойства для управления волной
внутрикадрового обновления — у AMD и Intel это приватные расширения их SDK.
На пути MFT устойчивость обеспечивается гарантированной доставкой TCP и
выдачей IDR по сообщению `PM_MSG_KEYFRAME_REQ`. Подробности — в разделе 5.2
документа по архитектуре.

## Требования

* Windows 10 1903+ или Windows 11, видеокарта с аппаратным кодированием H.264
* Android 8.0 (API 26)+ с аппаратным декодером H.264
* USB-кабель с поддержкой передачи данных, включённая отладка по USB
* Android SDK Platform-Tools (`adb`) — стример найдёт его сам
